### [P0-2] `_confirmAlive()`: UBI-Anspruch wird bei Escrow-Rückkehr dauerhaft vernichtet

**Datei:** `contracts/AequitasV7.sol:349` (identisch in root `AequitasV7.sol`)

**Problem:** Ein Mensch, der lange inaktiv ist, wird per `triggerEscrow()` in Escrow verschoben — zählt aber weiter zu `totalHumans` und häuft über `accumulateUBI()` (permissionless, von jedem aufrufbar) weiter UBI-Anspruch an. Während der Escrow-Zeit kann er `claimUBI()` nicht selbst aufrufen (`require(escrowOf[msg.sender] == 0)`). Kommt er über `confirmAlive()`/`guardianConfirmAlive()` zurück, überschreibt `_confirmAlive()` einfach `ubiClaimed[human] = ubiPerHumanAccumulated`, **ohne** vorher die Differenz (`ubiPerHumanAccumulated - ubiClaimed[human]`) gutzuschreiben — anders als der korrekte `claimUBI()`-Pfad. Das Geld wurde aber bereits aus `ubiPool` abgezogen und landet nirgends mehr.

**Empirischer Beweis:** Neuer Test `test/AequitasV7_confirmAlive_ubi_forfeiture.ts` (im Repo vorhanden, Contract nicht verändert). Ergebnis mit `npx hardhat test --build-profile production`:
```
AssertionError: confirmAlive() must credit the UBI owed at wake-up. balanceOf increased by
1900000000000000000000 but should have increased by 1905146849388001014713
(escrow 900 AEQ + wake-up bonus 1000 AEQ + owed UBI 5.146849388001014713 AEQ).
- Expected: 1905146849388001014713n
+ Received: 1900000000000000000000n
```
~5,15 AEQ pro Zyklus verschwinden spurlos — exakt der Betrag, der zuvor aus `ubiPool` abgezogen wurde. Bricht die Kern-Invariante `SUM(balanceOf) + SUM(escrowOf) + ubiPool == totalSupply`.

**Impact:** Passiert bei **jeder normalen** Escrow-Recovery mit ausstehendem UBI-Anspruch — kein Angriffsszenario nötig, sondern der erwartete Standardfall. Dieselbe Bug-Klasse wurde am 2026-07-05 bereits für `triggerEscrowToUBI` gefixt (`ForfeitedUBIRecycled`-Mechanismus), der Schwesterpfad in `_confirmAlive` wurde beim Fix übersehen.

**Fix:** Vor dem Überschreiben von `ubiClaimed[human]`: `owed = ubiPerHumanAccumulated - ubiClaimed[human]` berechnen (mit derselben Underflow-Absicherung wie in `claimUBI`) und zu `balanceOf[human]` addieren (nicht zu `totalSupply` — analog zur P0-5-Fix-Logik), dann erst `ubiClaimed[human]` setzen. Exakt spiegeln, was `claimUBI()` bereits korrekt macht.

### [P0-3] Unrecovered Goroutine hinter öffentlichem Peer-Registrierungs-Endpoint crasht den ganzen Node

**Datei:** `x/humanity/keeper/sync_blocks.go:255-262`, ausgelöst über `api.go:1935` (`handlePeerRegister` → `registerURLIfAuthorized` → `startSyncForPeer`)

**Problem:** Der pro-Peer-Sync-Goroutine (und die gesamte aufgerufene Kette: `syncWithNode`, `doSyncOnce`, `fetchBlocksSince`, `syncValidatorsFromPeer`) hat **kein** `recover()`. Die einzigen zwei `recover()`-Stellen im ganzen Paket sind unabhängig davon in `evm_engine.go:159,355`. Ein Panic in einer Goroutine kann in Go **nicht** von einem `recover()` in einer anderen Goroutine (z. B. der Request-Goroutine) aufgefangen werden — er beendet den kompletten Prozess.

**Impact:** `POST /api/peers/register` mit gültigem `PEER_SECRET` (oder aktiviertem `ALLOW_PEER_SECRET_BYPASS`) und einer URL, die eine bösartige oder einfach nur kaputte Antwort auf `/api/blocks`, `/api/validators` oder `/api/health/combined` liefert (z. B. falscher Typ, leeres Array wo ein Index erwartet wird, nil-Dereferenzierung tiefer im Block-Processing), kann den **gesamten Node-Prozess** zum Absturz bringen — nicht nur den Request. Erreichbar durch jeden, der die URL-Registrierung autorisiert bekommt (niedrigere Hürde als vollständiger Validator-Status), und auch unbeabsichtigt durch einen legitimen, aber fehlerhaften Peer.

**Fix:** `defer func(){ if r := recover(); r != nil { ... } }()` an den Anfang der `startSyncForPeer`-Goroutine (und als Verteidigung in der Tiefe an jede andere `go func(){...}()`-Hintergrundschleife in `api.go` — es gibt mind. 3 weitere in `NewAPIServer`). Zusätzlich: explizite `recover()`-Middleware um den HTTP-Mux legen (aktuell schützt nur die implizite Go-stdlib-Behandlung pro Verbindung, kein eigenes Sicherheitsnetz).

## P1 — HOCH (Sicherheitslücken / kritische Test-Infrastruktur)

### [P1-1] Hardhat-Default-Profil ohne Optimizer: Guardian/UBI-Testsuite deployt nicht

**Datei:** `hardhat.config.ts:6-10`

**Problem:** Das `default`-Solidity-Profil hat keine Optimizer-Einstellung. `npx hardhat test` (ohne Flags — der naheliegende Standardbefehl) kompiliert `AequitasV7.sol` dadurch auf **24.630 Bytes Runtime-Bytecode** — 54 Bytes über dem EIP-170-Limit von 24.576 Bytes. Jeder Contract-Deploy in `test/AequitasV7_guardian_ubi_fixes.ts` schlägt dadurch am Konstruktor fehl ("trying to deploy a contract whose code is too large"), maskiert als generischer RPC-Fehler.

**Selbst verifiziert:** Produktions-Bytecode (hardcodiert in `x/humanity/keeper/contract_deploy.go`, mit Optimizer/solc 0.8.35 kompiliert, Stand heute) ist nur **11.379 Bytes** — unkritisch, weit unter dem Limit. Mit `--build-profile production` laufen alle bestehenden Tests wieder grün (7/8 passing, einzige verbleibende „Fehler" ist der neue, absichtliche P0-1-Beweistest).

**Impact:** Kein Produktions-Deployment-Risiko, aber die sicherheitskritischste Testdatei des Projekts (Guardian/UBI-Edge-Cases, inkl. der Fixes vom 2026-07-05) liefert **mit dem dokumentierten Standardbefehl keinerlei Schutz** — niemand würde es ohne das `--build-profile production`-Flag bemerken.

**Fix:** `default`-Profil dieselben Optimizer-Einstellungen wie `production` geben, oder den `test`-Task fest auf das `production`-Profil verdrahten.

### [P1-2] Kein globales Panic-Recovery-Middleware auf dem HTTP-Mux

**Datei:** `x/humanity/keeper/api.go:400-526` (`Start`, `gzipMiddleware`)

**Problem:** `gzipMiddleware` ist die einzige Middleware um `mux` — sie recovert keine Panics. Ein einzelner Handler-Panic wird zwar durch Gos `net/http`-Stdlib-Verhalten abgefangen (nur diese eine Verbindung stirbt), aber es existiert kein explizites Sicherheitsnetz auf Mux-Ebene. Direkt verwandt mit P0-2: jede zukünftige Handler-Änderung, die eine Goroutine spawnt, reproduziert lautlos dieselbe Absturzgefahr.

**Fix:** Explizite `recover()`-Middleware um `mux` als Verteidigung in der Tiefe, und `go func(){...}()`-Aufrufe projektweit standardmäßig mit demselben Recover-Pattern versehen.
