# Umzug C1 auf einen kleineren Server — Ablaufplan (23.12.2026)

C1 ist der einzige Validator und trägt außerdem Datenbank, Proof-Server,
Coordinator und Vergleichsdienst (Biometrie). Ziel: alles auf einen
günstigeren Server, **mit denselben Schlüsseln** (die Validator-Adresse
`0x3066…42dc` bleibt, nichts muss neu gebunden werden), kurzer Pause der
Kette und einem jederzeit offenen Rückweg.

**Die eine Regel:** Alter und neuer C1 laufen **nie gleichzeitig** mit
demselben Schlüssel. Sonst unterschreiben zwei Knoten verschiedene Blöcke
derselben Höhe. Die Werkzeuge erzwingen das: `umziehen` hält zuerst alles
auf dem alten Server an und prüft, dass er schweigt; `zurueck` hält zuerst den
neuen an und prüft das; das Auspacken verweigert sich neben einem laufenden
`aequitas-node`.

## Werkzeuge (alle in diesem Repo, alle mit Freigabe `produktion`)

| Workflow | Was | Ändert etwas? |
|---|---|---|
| [`auslastung-c1.yml`](https://github.com/hanoi96international-gif/Aequitas/actions/workflows/auslastung-c1.yml) | CPU/RAM je Dienst auf C1, über bis zu 60 min | nein |
| [`neuer-c1-pruefen.yml`](https://github.com/hanoi96international-gif/Aequitas/actions/workflows/neuer-c1-pruefen.yml) | neuer Server: Host-Schlüssel gegen Eingabe, Kerne, RAM, Platz, Ports, Steal-Zeit, Signatur-Messung; dieselbe Messung auf C1 | nein |
| [`c1-umzug.yml`](https://github.com/hanoi96international-gif/Aequitas/actions/workflows/c1-umzug.yml) `inventar` | was auf C1 liegt (Namen, Pfade, Größen) | nein |
| `c1-umzug.yml` `vorbereiten` | neuer Server: Docker, Firewall, Repos, Images | nur der neue Server, startet nichts |
| `c1-umzug.yml` `probe` | verschlüsselter Transport alt → neu, zählen, wieder löschen | nein (C1 läuft weiter) |
| `c1-umzug.yml` `umziehen` | **ernst**: alt anhalten, packen, neu auspacken | ja — Bestätigung `C1 UMZIEHEN` |
| `c1-umzug.yml` `zurueck` | neu anhalten, alt wieder starten | ja — Bestätigung `ZURUECK` |
| `c1-umzug.yml` `aufraeumen` | Umzugsschlüssel auf dem neuen Server löschen | ja |
| `scripts/c1_ziel_wechseln.py` | IP + Host-Schlüssel in allen ~70 Dateien tauschen (PR) | Code |

Wie der Datenumzug geschützt ist: Der neue Server erzeugt selbst einen
age-Schlüssel; der alte verschlüsselt an dessen öffentlichen Teil. Der
GitHub-Runner sieht nur Chiffrat, das (öffentliche) Log nur Namen, Anzahlen,
Größen. age erkennt jede Veränderung und jeden Abbruch des Stroms.
Zwischenstände mit Klartext werden auch bei einem Abbruch gelöscht. Geprüft
in `scripts/test_umzug_c1.sh` (läuft im CI mit echtem Docker).

## Vorher (bis 22.12.)

1. **Messen.** `auslastung-c1.yml` mit `dauer=3600` laufen lassen, möglichst
   einmal zu einer belebten Zeit. Daraus die Größe des neuen Servers:
   Summe „RAM Spitze“ + 50 % Luft, Kerne ≥ 2 × „CPU Spitze“, mindestens
   4 **dedizierte** Kerne. Platz: belegt × 2 (das Auspacken braucht
   kurz die doppelte Menge).
2. **Bestellen.** Ubuntu 24.04, SSH-Schlüssel „Aequitas“ (derselbe wie für
   C1, `CONTABO_SSH_KEY`) beim Anbieter hinterlegen. **Host-Schlüssel aus der
   Konsole des Anbieters notieren** (`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`
   in der Web-Konsole) — nie vom Runner übernehmen.
3. **Prüfen.** `neuer-c1-pruefen.yml` mit IP und Fingerabdruck. Erwartet:
   Host-Schlüssel stimmt, Ports frei, Steal < 1 %, Signaturen in der
   Größenordnung von C1 (je Kern).
4. **Inventar.** `c1-umzug.yml` `inventar`. Prüfen: jeder Dienst hat seine
   Volumes/Pfade; Größen plausibel. Was dort nicht steht, zieht nicht mit.
5. **Vorbereiten.** `c1-umzug.yml` `vorbereiten` (neuer Server: Docker,
   Firewall, Repos, Images). Startet nichts.
6. **Proben, mehrmals.** `c1-umzug.yml` `probe`. Erwartet im Log:
   `Soll: N Dateien … Ist: N Dateien …` und `Probe gut`. **Dauer notieren** —
   so lange steht die Kette am Umzugstag (plus Start, ca. 10 min).
7. **Ziel-PR vorbereiten, nicht mergen.** Auf einem Zweig:
   `python3 scripts/c1_ziel_wechseln.py --neu-ip <IP> --neu-fp <SHA256:…> --schreiben`,
   PR öffnen, CI grün (prüft: eine IP, ein Host-Schlüssel überall, Seeds und
   Bootstrap gleich). **Nicht** mergen — der Merge löst den Deploy aus.
8. **DNS-TTL senken** (24 h vorher, also am 22.12.) für `aequitas.digital`
   und `proof1.aequitas.digital` auf 300 s, damit der Wechsel schnell greift.
9. **Sicherungen frisch:** `backup-ledger.yml`, `backup-biometrie-verschluesselt.yml`,
   `schluessel-sichern.yml` am 22.12. laufen lassen (Rückfall, falls beide
   Server ausfallen).

## Rückweg (jederzeit, bis der alte Server gelöscht ist)

1. DNS zurück auf `188.172.229.121`.
2. `c1-umzug.yml` `zurueck` (IP + Fingerabdruck des neuen, Bestätigung
   `ZURUECK`): hält **zuerst** alles auf dem neuen Server an, prüft, dass er
   schweigt, startet dann auf dem alten, was vorher lief (mit der alten
   Neustart-Regel), und wartet, bis er antwortet.
3. Ziel-PR rückgängig machen (Revert-PR), damit Workflows wieder den alten
   Server meinen.

Achtung: Blöcke, die der neue Server schon erzeugt hat, kennt der alte nicht.
Ein Rückweg **nach** Schritt 3 verliert sie — deshalb die Abnahme gründlich
und bald machen, und den Rückweg nach Möglichkeit nur vor Schritt 3 nehmen.

## Danach

  alten Server beim Anbieter **neu installieren lassen** (Datenträger
  überschreiben) und kündigen — dort lagen alle Schlüssel.
- Die alte IP steht nach dem Ziel-PR in `scripts/lint_alte_hosts.py`:
  kein Workflow darf sie mehr ansprechen (der Anbieter vergibt sie neu).
- Übergabe (`docs/SITZUNG_UEBERGABE.md`) und `docs/LAUNCH_CHECKLISTE.md`
  auf den neuen Server.

## Fehlerbilder

| Bild | Ursache | Abhilfe |
|---|---|---|
| `neuer-c1-pruefen`: „Host-Schlüssel passt NICHT“ | Fingerabdruck falsch abgeschrieben, oder ein anderer Rechner antwortet | in der Anbieter-Konsole neu ablesen; nie den gesehenen Wert übernehmen |
| „Anmeldung per Schlüssel scheitert“ | SSH-Schlüssel „Aequitas“ nicht hinterlegt | beim Anbieter hinterlegen, Image neu installieren |
| `probe`/`umziehen`: „ZAEHLUNG WEICHT AB“ | Strom unvollständig, Platte voll | Platz prüfen (`neuer-c1-pruefen`), wiederholen; bei `umziehen`: `zurueck` |
| `umziehen`: „Knoten antwortet noch -- Abbruch“ | Container ließ sich nicht anhalten | Log lesen; nichts wurde übertragen; `zurueck` startet wieder |
| „Hier läuft schon ein Knoten“ | auf dem neuen Server läuft `aequitas-node` | dort anhalten (nie zwei gleichzeitig), dann wiederholen |
| „Hier wurde schon ein Umzug ausgepackt“ | zweiter Lauf | Absicht prüfen; der erste Stand ist schon da |
| Deploy: Höhe steigt nicht | Datenbank nicht passend / Peers | `log-lesen.yml`, `haenger-diagnose.yml`; sonst `zurueck` vor dem DNS-Wechsel |
