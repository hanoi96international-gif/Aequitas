## Der Biometrie-Strang — der harte Launch-Blocker

Gemessen am 19.08. auf **beiden** Validatoren, identisch:

```
BIO_ATTESTATION_MODE=off (unset, the default)
COORDINATOR_PUBLIC_KEYS present: 0
```

Die Kette live:

```
32 zufällige Bytes je App-Installation   (aequitas-app/lib/identity.ts, ensureDeviceSecret)
  → deriveBioHash → bio
  → /prove          (Gate aus)
  → nullifier = Poseidon(bio)      (biometric_v3.circom; bio ist ein privater
                                    Input, den der Circuit NICHT prüft)
  → Kette registriert „verifizierten Menschen" → 1.000 AEQ + UBI
```

`bio_attestation.js` benennt es selbst: ein Angreifer *„does not defeat it, they
skip it. They pick their own scalar, call /prove, and receive a valid
nullifier."*

**Warum das kein Flag-Problem ist:** `optional` und `required` verlangen
mindestens einen Koordinator-Schlüssel. Das GitHub-Repo
`aequitas-biometric-beta` enthält nur eine README („Leer. Kein Code, keine
Daten, keine Abhängigkeiten"). Der Betreiber gibt an, der Code liege lokal unter
`C:\Users\aequitas-biometric-beta` — **er ist nie gepusht worden**. Solange das
so ist, kann keine Sitzung damit arbeiten.

In der App: `EXPO_PUBLIC_BIOMETRIC_ENABLED` ungesetzt,
`EXPO_PUBLIC_COORDINATOR_BASE` steht in `eas.json` als Platzhalter
`https://<dein-coordinator-host>`. Der Biometrie-Pfad (`biometric-capture.tsx`,
`lib/biometricIdentity.ts`) existiert und ist verdrahtet, wird in
ausgelieferten Builds aber nicht betreten.

`x/humanity/mpc/` (1.391 Zeilen, Hamming-Distanz über Secret Shares, öffnet nur
das Bit „ähnlich/nicht ähnlich") ist **von nichts importiert**.

**Reihenfolge zum Schließen, nicht verhandelbar:** Koordinator pushen und bauen
→ `optional` mit ausgelieferten Schlüsseln → App-Build, der Bestätigungen holt
→ `required`. Direkt auf `required` sperrt jede installierte App aus.

Die Korrektur im Whitepaper (§3.2) beschreibt genau diesen Zustand — sie liegt
auf dem Branch und ist **noch nicht gemerged**.

## Geldmenge — Forderung des Betreibers: exakt 15.000 bei 15 Menschen

Gemessen 19.08., **beide Boxen byte-identisch**:

| | |
|---|---|
| `supply_measured` | 15.305,278008 AEQ |
| `total_supply` (Regel: 15 × 1.000) | 15.000,00 AEQ |
| `supply_difference` | **+305,278008 AEQ** |

Zwei getrennte Fragen, die nicht vermischt werden dürfen:

**a) Die 305 AEQ.** Der Reconciliation-Lauf zeigt hunderte Nicht-Menschen-Konten
(`is_human = false`) mit jeweils ~0,001 AEQ, absteigend bis 0,000070. 305,278 /
0,001 ≈ 305.000 Konten — das passt auf Loadtest-Rückstände. **Zu bestätigen:**
die Summenzeilen `sum_balance_humans`, `sum_balance_non_humans`,
`pool_reserve_aeq` aus Abschnitt 1–3 von `supply-reconciliation.yml` (im langen
Kontodump untergegangen — beim nächsten Lauf gezielt herausziehen). Bestätigt
sich das, ist es **kein Mint**, sondern nicht zurückgeholtes Testgeld, und ein
Sweep dieser Konten erfüllt die Forderung ohne Eingriff in die Konsenslogik.

**b) Die +4 µAEQ.** `supply_measured.go` dokumentiert 15.305,278004 für den
15.08.; heute steht dort …008. Vier Tage, vier Tagesrunden, +1 µAEQ pro Runde.
Die Datei setzt das Kriterium selbst: *„If it ever starts moving, that is a live
mint."* Ausgeschlossen ist bereits: Knotendivergenz (beide Boxen gleich), die
drei Tagesverteilungen (alle `floor6` + Pool nullen — **vernichten** Reste), und
der 40/30/20/10-Split (`tMicro = feeMicro - vMicro - lMicro - uMicro`, exakt
per Konstruktion). **Bleibt zu prüfen:** Demurrage-Settlement, Wealth Cap,
Persistenz-Rundung beim Speichern.

Anforderung des Betreibers ausdrücklich auch für den AMM: die Invariante muss
halten, wenn der Swap-Preis sich bewegt. `MeasuredTotalAEQ` zählt
`sum(chain_accounts.balance) + liquidity_pool.reserve_aeq`, ein Swap ist damit
per Konstruktion neutral — die Conservation-Tests decken das ab.

## Weitere offene Funde

**Nullifier-Zuordnung entartet.** Aus dem Reconciliation-Lauf:

```
-- any wallet holding more than one nullifier (must be empty):
0x0000000000000000000000000000000000000001|14
```

Vierzehn der fünfzehn Nullifier hängen an derselben Platzhalter-Adresse. Dazu
passt `register_human_txs_in_plain_blocks: 1` — nur **eine**
Registrierungs-Transaktion ist in den Blöcken auffindbar. Die Zählungen stimmen
(15/15/15 distinkt), aber wem welche Registrierung gehört, weiß die Kette für 14
Fälle nicht.

**7 gegen 15.** Beide Proof-Server melden `bio_hash_count: 7`, die Kette 15
Menschen.

**DB-GUARD feuert live** auf Contabo2, bei jedem Peer-Block:
`AddPeerBlock → IsValidatorSuspended → loadPenaltyCacheLocked` schreibt aus einer
fremden Goroutine, während eine andere die aktive Transaktion hält. Der Guard
fängt es ab, der Pfad ist nicht auf explizites ctx/tx migriert.

**Die Boxen sind nicht baugleich.** Nur Contabo2:
`AEQUITAS_COMPRESS_BLOCK_PAYLOAD`, `AEQUITAS_WAL_ENABLED` (verifiziert aktiv:
`[WAL] ✓ WAL fast path active`), `AEQUITAS_WAL_PATH`, `AEQUITAS_DB_MAX_CONNS`,
`AEQUITAS_PRODUCE_WHEN_BACKLOG_SHRINKING`, `ENABLE_MULTI_BLOCK_TICK`,
`BOOTSTRAP_SNAPSHOT_URL`, `RELAYER_ADDRESS`. Nur Contabo1: `IS_PRIMARY_NODE`,
`RESYNC_FROM_SNAPSHOT` (Wert maskiert — **nachsehen**, es gibt einen eigenen
Workflow `fix-resync-from-snapshot-flag.yml`). WAL und Multi-Block-Tick tragen
im eigenen Code „NOT staging-validated" und laufen auf der Box, die die einzige
zweite Kopie des Ledgers hält.

**K2 unverändert offen.** Der StateRoot ist keine Konsensregel: bei Abweichung
wird der Block trotzdem übernommen. Am 25.07. gemessen: 150 Mismatches in 10
Minuten, stabil unterschiedliche Werte. Nächster Schritt bleibt die read-only-
Messung aus `ANALYSE_STATEROOT_DIVERGENZ.md` Abschnitt G.

## Nur der Betreiber kann

1. **Koordinator-Code pushen** (`C:\Users\aequitas-biometric-beta`). Ohne das ist
   der Personhood-Blocker für jede Sitzung unerreichbar.
2. **DNS von Railway wegziehen.** Auto-renew ist seit dem Abholen des
   Transfer-Codes **aus**, die Subscription ist überfällig, Railway serviert
   weiterhin das DNS (`ns1kpv…ns4fpy.name.com`) für `@`, `www`, `proof1`,
   `proof2`. Jede installierte App hat den Namen fest verdrahtet. Reihenfolge:
   Betrag zahlen → Zone beim neuen Anbieter anlegen (A `@`/`www`/`proof1` →
   173.249.37.118, A `proof2` → 194.163.188.71, TTL 300) → Custom Nameservers →
   verifizieren → **dann** EPP-Code einlösen → Auto-renew wieder an.
   Der in der Sitzung geteilte EPP-Code sollte rotiert werden.
3. **Externes Contract-Audit.** Das eigene Audit fand eine P0-Mint-Lücke, die
   live war (`nullifierMatchesProof` implementiert, getestet, **nie
   aufgerufen**).
4. **Entscheiden**, ob Kompression auf Contabo2 an bleibt: gemessen 3,5× schneller
   beim Speichern, kostet aber die Möglichkeit, diese Box gefahrlos auf einen
   Build vor dem Codec zurückzurollen.
5. **Die Tagesrunde** auf einem Zwei-Knoten-Netz entscheiden.

## Einschätzung zur Launchfähigkeit

Die Chain läuft: beide Validatoren gesund, synchron, produzierend, alle
heutigen Vorfälle abgeschlossen, volle Testsuite grün.

„Launchfähig" im Sinne von *Proof of Humanity* ist sie nicht. Was zum Start
registriert wird, ist ein Gerät — und ohne Gate nicht einmal das, sondern eine
frei gewählte Zahl. Das Whitepaper sagt das in §3.2 nach der Korrektur
vollständig. Mit dieser Ehrlichkeit ist ein Launch als das, was es ist,
vertretbar; als „Geldmenge = Funktion menschlicher Existenz" ist er es nicht,
solange Punkt 1 offen ist.
