# Launch runbook — 2026-08-18

The launch is on 2026-08-18. The switch gets one attempt. Everything that can
be verified in advance was verified on 2026-08-15 and is listed here as
*already done*, so launch day is a short sequence rather than a discovery
exercise.

**Correction to an earlier reading of this date.** `aequitas.digital` does not
"become available" on 2026-08-18 — it is already registered to us, and Railway
already manages its DNS (name.com nameservers, records visible in the Railway
domain panel). What ends on 2026-08-18 is ICANN's 60-day registrar lock: the
first day the domain *could* be transferred away from Railway to another
registrar. That is independent of everything below. DNS records can be edited
today and could have been edited yesterday, so no step here waits on it.

Two consequences worth stating plainly:

- **Do not transfer the registrar on launch day.** A transfer takes days, needs
  the auth code, and moves DNS control while Let's Encrypt is issuing. Launch
  first on the DNS we already control, transfer when the network is quiet.
- **Railway cannot be torn down while it serves this DNS.** The migration doc
  calls Railway "abgeschaltet", and it hosts no service — but the domain's
  nameservers still point at it. Deleting that account before the domain is
  transferred, or before the nameservers are moved elsewhere, takes
  `aequitas.digital` off the internet.

## What the app depends on

`aequitas-app/lib/config.ts` hardcodes three endpoints, all on the domain:

```
API_BASE = https://aequitas.digital/api
RPC_URL  = https://aequitas.digital/rpc
WEBAPP   = https://aequitas.digital
```

They are overridable at build time via `EXPO_PUBLIC_*`, but no shipped build
sets them. So the domain must resolve to Contabo1 and serve TLS before any app
install works. Nothing else in the system depends on the name: the validators
find each other by IP, and the node prefers a verified validator address over
the canonical domain when seeding (4b2a780).

## The sequence

1. **DNS.** All of it happens in the Railway domain panel, which is where this
   domain's records live (name.com nameservers, Railway-managed). Read live on
   2026-08-18: `aequitas.digital` -> 69.46.46.73, `www` does not resolve at
   all, `proof1` -> 173.249.37.118 (correct already).

   | Record | Name | Content | Action |
   |---|---|---|---|
   | ANAME | `@` | Railway target (`bk86j…`) | **delete** — this is what makes the domain resolve to 69.46.46.73, and an apex cannot hold an ANAME and an A record at once |
   | A | `@` | `173.249.37.118` | **add** |
   | A | `www` | `173.249.37.118` | **add** — the Caddyfile serves `www` too, and without this record Caddy retries a certificate for it forever |
   | TXT | `_railway…` | Railway verification | leave |
   | A | `proof1` | `173.249.37.118` | leave |
   | A | `proof2` | `194.163.188.71` | leave |

   Keep the TTL low for the first day (the panel's 300s default is fine).

   While in that panel, check that **auto-renew is on**. The domain expires
   2027-06-19, and the shipped app has all three of its endpoints hardcoded to
   this name — an expiry takes the network's public face down with no code
   change to blame.
2. **Wait for propagation.** `getent hosts aequitas.digital` must return
   173.249.37.118. The install workflow refuses to run until it does — that
   guard exists because Caddy would otherwise retry a certificate forever for a
   name that resolves elsewhere.
3. **Run `Serve aequitas.digital from Contabo1`** (workflow_dispatch). It
   backs up the current Caddyfile, validates the new one *before* swapping so
   `proof1.aequitas.digital` cannot be taken down by a bad config, reloads, and
   then waits for the certificate.
4. **Verify** — all three must be true:
   - `curl -s https://aequitas.digital/api/status` reports the real chain
     (height in the millions, `total_humans` 15+), not a small number
   - `curl -s https://proof1.aequitas.digital/health` still returns
     `{"status":"ok",...}`
   - the app's own three endpoints resolve: `/api/status`, `/rpc` (a JSON-RPC
     POST), and the landing page
5. **Announce — only after step 4 passes.** Ready-to-post text for X
   (`@AequitasMoney`) and the Telegram group is in
   [`docs/LAUNCH_POSTS_2026-08-18.md`](LAUNCH_POSTS_2026-08-18.md). Every post
   there links to `aequitas.digital`, so posting ahead of the certificate
   points the first audience this project has at a dead name.

## Done — 2026-08-18 06:03 UTC

The switch is live. `aequitas.digital` and `www` resolve to Contabo1, Caddy
holds a Let's Encrypt certificate for both, and the domain serves the real
chain. Measured by the install workflow's own acceptance checks:

```
height=4069348  total_humans=15  chain_evm_id=1926
/rpc  eth_chainId -> {"id":1,"jsonrpc":"2.0","result":"0x786"}
GET / -> 200      www -> 200      proof1 -> 200
```

Height 4,069,348 is the point: the host this domain used to answer from was
serving height 96. A status code alone would not have told them apart, which
is why the workflow now asserts the numbers.

**It took two attempts, and the first one is worth recording.** The install
step ran `mv /etc/caddy/Caddyfile.new /etc/caddy/Caddyfile` inside
`proof-caddy`. That file is a bind mount, and `rename()` onto a mount point
fails with EBUSY — so the swap could never have worked on this box, in any
run, and only a real run could show it. Nothing was damaged: `caddy validate`
had already passed, the old config stayed in place, proof1 kept serving, and
the job stopped before the reload. The fix writes through the existing inode
(`cat new > Caddyfile`) instead of renaming.

Between the DNS change and the successful run, the domain pointed here with
no site configured for it, so browsers showed a TLS error for a few minutes.
That window is unavoidable in this order and is the reason step 5 says to
announce only after step 4 passes.

## If something goes wrong

- **Certificate does not issue.** Check that DNS really resolves to Contabo1
  from outside, and that port 80 reaches `proof-caddy` (it does today). Caddy
  retries on its own; nothing needs restarting.
- **`aequitas.digital` answers 502.** Caddy is up but cannot reach the node.
  Preflight step 3 covers exactly this; re-run it.
- **Roll back.** The install copies the previous config to
  `/etc/caddy/Caddyfile.bak-<timestamp>` inside the container. Restore it and
  `caddy reload` to return to the proof1-only state.

## Resolved on 2026-08-16

- **Contabo2 recovered and disarmed.** It had come back on its own and was
  following the chain, but a failed resync had left `RESYNC_FROM_SNAPSHOT` live
  in its RUNNING container — the next ordinary deploy would have thrown that
  away. Removed via `Normalize node env`; the node stayed up and advancing.
- **Contabo1 can no longer self-wipe.** `RESYNC_FROM_SNAPSHOT` and
  `BOOTSTRAP_SNAPSHOT_URL` (which pointed at Contabo2) are gone from both the
  running container and `/root/.aequitas.env`, so the next deploy cannot restore
  them. Its auto-heal now reports: *"Disabled: … refusing to self-wipe without a
  trusted, signed snapshot source."* Contabo2 keeps its source, which points at
  Contabo1 — the correct direction — and now with Contabo1's real signing
  address.
- **A backwards resync is refused in code**, not by accident. See
  `resyncBackwardsTolerance`.
- **`git_commit` reads a real commit** on both nodes instead of "unknown", so
  the fleet-version comparison works.
- **The Network tab can actually verify a peer.** Its cross-origin reads were
  refused by the page's own CSP; the node now answers `/api/peers/status` on the
  page's behalf. This also survives the HTTPS switch below, where those reads
  would additionally have been mixed content.
- Both validators verified byte-identical after every change.

### Contabo1's snapshot source was Contabo2 — FIXED 2026-08-16

Kept here because it is the sharpest near-miss of the whole audit, and
because the arrangement that produced it can come back through any config edit. Measured 2026-08-15 from both boxes' own configuration:

```
Contabo1:  BOOTSTRAP_SNAPSHOT_URL = http://194.163.188.71:8080/api/snapshot   (= Contabo2)
           RESYNC_FROM_SNAPSHOT   = false        (in the env file — the safe state)
           …but its own log carries:
           [RESYNC] RESYNC_FROM_SNAPSHOT=true — replacing local state from …194.163.188.71…
           [RESYNC] ✗ Resync failed: snapshot server returned HTTP 429

Contabo2:  BOOTSTRAP_SNAPSHOT_URL = http://173.249.37.118:8080/api/snapshot   (= Contabo1, correct)
           RESYNC_FROM_SNAPSHOT   = true         (the deliberate arming switch; deploy_safe_c2.sh
                                                  strips it on ordinary deploys)
```

So the authoritative validator is configured to reseed itself **from the other
one**, and there is a boot on record where it tried. It failed on a rate limit.
The other protection is accidental: `BOOTSTRAP_SIGNER` is `0x92cbedec…` on both
boxes while the snapshots are actually signed by the serving node's own key
(`0x0be8b961…` from Contabo2, `0x1a37dcda…` from Contabo1), so every resync
attempt is refused at the signature check. That mismatch is currently the only
thing standing between a restart and Contabo1 replacing 3.8 million blocks with
whatever Contabo2 is serving — which, on 2026-08-15, was a chain of height 1.

What was done, 2026-08-16:

1. `BOOTSTRAP_SNAPSHOT_URL` removed from Contabo1 — container AND
   `/root/.aequitas.env`, so a deploy cannot restore it. Its auto-heal now
   refuses to self-wipe for want of a trusted source.
2. `RESYNC_FROM_SNAPSHOT` removed from both running containers and pinned to
   `false` in Contabo1's file. Contabo2's file keeps `true` as the deliberate
   arming switch its own deploy path strips.
3. `resyncBackwardsTolerance` refuses a snapshot far below local height in
   code, so this no longer depends on a signer mismatch nobody planned.

Contabo2 was NOT rebuilt in the end: it had already recovered on its own and
was byte-identical with Contabo1. The resync workflow was started before that
was known, wiped it, and failed during import — the node came back from its
own peers within minutes. Verified byte-identical afterwards.

### The daily round: what is and is not wrong

CORRECTION. An earlier version of this file read `last_ubi_at` (19 days old) as
"18 missed rounds of UBI". That was wrong.
`RunDailyDistributionAtomic` stamps that timestamp only `if ubiTotal > 0`
(state.go), so a round that runs correctly and finds the pools empty leaves it
untouched on purpose. The four pools hold 0.0000 / 0.0000 / 0.0000 / 0.2227 AEQ:
fifteen wallets and no trading generate almost no fees, so there has been
nothing to distribute. An old `last_ubi_at` is the expected state of a quiet
chain, not a fault.

What IS real, from Contabo2's log:

```
[POOLS] ✗ Skipping distribution this round: peers are configured but this node has
        never successfully synced a block from any of them
```

`lastSuccessfulPeerSyncAt` only advances on a successful *foreign merge* and is
process-local, so it resets to zero on every restart. A node that restarts and
reaches its slot before merging anything from a peer declines the round; on a
two-validator network with one node down, the survivor can decline indefinitely.
The gate is defensible — validator rewards are weighted by `blocks_produced`
from local state, so distributing on a partial view pays the wrong people — but
its behaviour when one validator is the only one left deserves a decision rather
than luck.

Not changed before launch, deliberately. What changed instead:
`/api/health/combined` now carries `distribution`, reporting what the scheduler
actually decided (`ran` / `skipped` / `failed`, with the reason) and flagging
only the condition that is genuinely a fault — rounds being reached and none of
them executing. It does not treat "nothing was paid out" as a problem.

## Known and accepted at launch

- **Biometric dedup caches are incomplete for the 15 pre-migration humans.**
  They registered against the previous primary and arrived on both validators
  as blocks, which carry no raw biometric hash — only the nullifier. The
  chain-side `bio_hashes` index and the proof servers' caches therefore start
  from the next API-path registration onward. The authoritative check is
  unaffected: all 15 nullifiers are on-chain and claimed atomically with the
  registration, so a repeat registration still fails — later and with a less
  helpful message than a warm cache would give. See `bio_hash_backfill.go`.
- **`git_commit` reports `unknown`** on both nodes, so the explorer's
  "is every node on the same build?" comparison cannot work. Cosmetic, but it
  is a diagnostic the Network tab offers and cannot currently deliver.
- **No future-drift validation on `block.Timestamp`.** A proposer-supplied
  timestamp is not checked against the local clock anywhere. The demurrage
  clock no longer trusts it (it is clamped to now), but the gap itself is open
  and wants a drift budget chosen against real inter-node skew.
