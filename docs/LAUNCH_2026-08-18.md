# Launch runbook — 2026-08-18

The domain `aequitas.digital` becomes available on 2026-08-18 and the launch is
the same day. The switch therefore gets one attempt. Everything that can be
verified in advance was verified on 2026-08-15 and is listed here as *already
done*, so launch day is a short sequence rather than a discovery exercise.

## What the app depends on

`aequitas-app/lib/config.ts` hardcodes three endpoints, all on the domain:

```
API_BASE = https://aequitas.digital/api
RPC_URL  = https://aequitas.digital/rpc
WEBAPP   = https://aequitas.digital
```

They are overridable at build time via `EXPO_PUBLIC_*`, but no shipped build
sets them. So the domain must resolve to Contabo1 and serve TLS before any app
install works. Nothing else in the system depends on the name: the validators
find each other by IP, and the node prefers a verified validator address over
the canonical domain when seeding (4b2a780).

## Verified in advance (2026-08-15)

Run `Domain switch preflight (read-only)` to re-confirm any of this at any
time — it changes nothing.

| Check | Result |
|---|---|
| `proof-caddy`, `aequitas-node`, `proof-server` containers exist on Contabo1 | ok |
| Caddy and the node share a docker network (`aequitas-net`) | ok — **no network change needed on the day** |

| `caddy validate` works in that container (the pre-swap safety gate is real) | ok |

The only step that cannot be rehearsed is certificate issuance, because
Let's Encrypt's HTTP-01 challenge needs the DNS record to exist.

## The sequence

1. **DNS.** Point `aequitas.digital` (and `www`) at **173.249.37.118**
   (Contabo1) with an A record. Keep the TTL low for the first day.
2. **Wait for propagation.** `getent hosts aequitas.digital` must return
   173.249.37.118. The install workflow refuses to run until it does — that
   guard exists because Caddy would otherwise retry a certificate forever for a
   name that resolves elsewhere.
3. **Run `Serve aequitas.digital from Contabo1`** (workflow_dispatch). It
   backs up the current Caddyfile, validates the new one *before* swapping so
   `proof1.aequitas.digital` cannot be taken down by a bad config, reloads, and
   then waits for the certificate.
4. **Verify** — all three must be true:
   - `curl -s https://aequitas.digital/api/status` reports the real chain
     (height in the millions, `total_humans` 15+), not a small number
   - `curl -s https://proof1.aequitas.digital/health` still returns
     `{"status":"ok",...}`
   - the app's own three endpoints resolve: `/api/status`, `/rpc` (a JSON-RPC
     POST), and the landing page

## If something goes wrong

- **Certificate does not issue.** Check that DNS really resolves to Contabo1
  from outside, and that port 80 reaches `proof-caddy` (it does today). Caddy
  retries on its own; nothing needs restarting.
- **`aequitas.digital` answers 502.** Caddy is up but cannot reach the node.
  Preflight step 3 covers exactly this; re-run it.
- **Roll back.** The install copies the previous config to
  `/etc/caddy/Caddyfile.bak-<timestamp>` inside the container. Restore it and
  `caddy reload` to return to the proof1-only state.

## Must be resolved before launch

### Contabo1's snapshot source is Contabo2

Measured 2026-08-15 from both boxes' own configuration:

```
Contabo1:  BOOTSTRAP_SNAPSHOT_URL = http://194.163.188.71:8080/api/snapshot   (= Contabo2)
           RESYNC_FROM_SNAPSHOT   = false        (in the env file — the safe state)
           …but its own log carries:
           [RESYNC] RESYNC_FROM_SNAPSHOT=true — replacing local state from …194.163.188.71…
           [RESYNC] ✗ Resync failed: snapshot server returned HTTP 429

Contabo2:  BOOTSTRAP_SNAPSHOT_URL = http://173.249.37.118:8080/api/snapshot   (= Contabo1, correct)
           RESYNC_FROM_SNAPSHOT   = true         (the deliberate arming switch; deploy_safe_c2.sh
                                                  strips it on ordinary deploys)
```

So the authoritative validator is configured to reseed itself **from the other
one**, and there is a boot on record where it tried. It failed on a rate limit.
The other protection is accidental: `BOOTSTRAP_SIGNER` is `0x92cbedec…` on both
boxes while the snapshots are actually signed by the serving node's own key
(`0x0be8b961…` from Contabo2, `0x1a37dcda…` from Contabo1), so every resync
attempt is refused at the signature check. That mismatch is currently the only
thing standing between a restart and Contabo1 replacing 3.8 million blocks with
whatever Contabo2 is serving — which, on 2026-08-15, was a chain of height 1.

Before launch:

1. Rebuild Contabo2 from Contabo1 (`Resync Contabo2 from Contabo1`, confirm
   `RESYNC-C2`). That workflow also sets `BOOTSTRAP_SIGNER` from Contabo1's
   actual signing address, so the signature check starts working as intended
   rather than by accident.
2. Decide what Contabo1's snapshot source should be. Pointing the authority at
   a secondary is only safe while the signer check happens to fail. Either
   remove `BOOTSTRAP_SNAPSHOT_URL` from Contabo1 entirely, or point it at an
   archive that is not a live validator.
3. Confirm `RESYNC_FROM_SNAPSHOT=false` reaches Contabo1's *container*, not just
   its env file.

### The daily round: what is and is not wrong

CORRECTION. An earlier version of this file read `last_ubi_at` (19 days old) as
"18 missed rounds of UBI". That was wrong.
`RunDailyDistributionAtomic` stamps that timestamp only `if ubiTotal > 0`
(state.go), so a round that runs correctly and finds the pools empty leaves it
untouched on purpose. The four pools hold 0.0000 / 0.0000 / 0.0000 / 0.2227 AEQ:
fifteen wallets and no trading generate almost no fees, so there has been
nothing to distribute. An old `last_ubi_at` is the expected state of a quiet
chain, not a fault.

What IS real, from Contabo2's log:

```
[POOLS] ✗ Skipping distribution this round: peers are configured but this node has
        never successfully synced a block from any of them
```

`lastSuccessfulPeerSyncAt` only advances on a successful *foreign merge* and is
process-local, so it resets to zero on every restart. A node that restarts and
reaches its slot before merging anything from a peer declines the round; on a
two-validator network with one node down, the survivor can decline indefinitely.
The gate is defensible — validator rewards are weighted by `blocks_produced`
from local state, so distributing on a partial view pays the wrong people — but
its behaviour when one validator is the only one left deserves a decision rather
than luck.

Not changed before launch, deliberately. What changed instead:
`/api/health/combined` now carries `distribution`, reporting what the scheduler
actually decided (`ran` / `skipped` / `failed`, with the reason) and flagging
only the condition that is genuinely a fault — rounds being reached and none of
them executing. It does not treat "nothing was paid out" as a problem.

## Known and accepted at launch

- **Biometric dedup caches are incomplete for the 15 pre-migration humans.**
  They registered against the previous primary and arrived on both validators
  as blocks, which carry no raw biometric hash — only the nullifier. The
  chain-side `bio_hashes` index and the proof servers' caches therefore start
  from the next API-path registration onward. The authoritative check is
  unaffected: all 15 nullifiers are on-chain and claimed atomically with the
  registration, so a repeat registration still fails — later and with a less
  helpful message than a warm cache would give. See `bio_hash_backfill.go`.
- **`git_commit` reports `unknown`** on both nodes, so the explorer's
  "is every node on the same build?" comparison cannot work. Cosmetic, but it
  is a diagnostic the Network tab offers and cannot currently deliver.
- **No future-drift validation on `block.Timestamp`.** A proposer-supplied
  timestamp is not checked against the local clock anywhere. The demurrage
  clock no longer trusts it (it is clamped to now), but the gap itself is open
  and wants a drift budget chosen against real inter-node skew.
